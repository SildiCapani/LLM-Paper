\subsection{Study Design}
We use a full factorial design with three fixed factors: \emph{LLM} (three levels),
\emph{programming language} (Python, Java, C++), and \emph{hardware platform} (laptop,
server, Raspberry~Pi~5). Programming tasks (14) are treated as a random factor, and each
task--LLM--language combination is sampled $k=5$ times, yielding
$3 \times 3 \times 14 \times 5 = 630$ generated programs. Every functionally correct
program is executed on all three platforms. The dependent variables are energy consumption
(primary), execution time, peak memory usage, and functional correctness.

\subsection{LLMs and Access via Official Coding CLIs}
\label{sec:llms}
We study the flagship models of the three most widely used commercial AI assistants:
Claude (Anthropic), ChatGPT (OpenAI), and Gemini (Google). Rather than querying the bare
models through their APIs, we access each model through its vendor's official command-line
coding agent (Claude Code, Codex CLI, Gemini CLI), authenticated with a regular
subscription (\cref{tab:llms}). This reflects how developers increasingly obtain generated
code in practice; the factor \emph{LLM} therefore denotes the combination of model and
official tool. Open-weight models, which lack a comparable official subscription-based
coding CLI, are left to future work, so that all levels of the factor share the same mode
of access.

To isolate the models' code generation from agentic behaviour, every request is issued
non-interactively in a fresh, empty working directory, without user configuration, project
context files, or session history, and with tool use disabled where the CLI supports it
(Claude Code, Gemini CLI) or restricted to a read-only sandbox otherwise (Codex CLI). The
CLIs' built-in system prompts are left unchanged. We log every request's full event stream
and report whether any tool was invoked. Details are given in \cref{sec:generation}.

\subsection{Programming Tasks}
\label{sec:tasks}
The task set (\cref{tab:tasks}) combines two complementary sources.

\paragraph{EffiBench-X tasks (algorithm free).}
Ten tasks are drawn from EffiBench-X~\cite{qing2025effibenchx}, which provides problem
statements, test-case generators including stress inputs, and canonical solutions in Python,
Java, and C++. We restrict the pool to the 244 function-style problems (originally from
LeetCode) of difficulty \emph{Medium} or \emph{Hard} for which starter code, a canonical
solution, and a test runner exist in all three languages. The selection is stratified by
category and difficulty: for each of five categories, defined by the problems' LeetCode
tags, one Medium and one Hard problem is drawn uniformly at random (seed \texttt{20261025});
a problem drawn for one category is removed from the pool for the following categories.
Since problems often carry several tags, the categories describe the selection strata
rather than an exclusive classification.

Function-style tasks let all LLMs share the same, language-specific input/output harness
supplied by EffiBench-X, so differences in measured energy stem from the generated
solution rather than from differing I/O code. The LLM is free to choose any algorithm.

\paragraph{CLBG tasks (algorithm prescribed).}
Four tasks are taken from the Computer Language Benchmarks Game (CLBG): \texttt{n-body},
\texttt{spectral-norm}, \texttt{binary-trees}, and \texttt{fannkuch-redux}. They are
CPU- and memory-intensive, scale to arbitrary input sizes, and link our study to prior work
on language energy efficiency~\cite{pereira2017energy,pereira2021ranking}. In contrast to
the EffiBench-X tasks, their specifications prescribe the algorithm, so differences between
LLMs reflect implementation choices only. We rewrote the specifications as self-contained
task descriptions and verified them with our own reference implementations against the
official CLBG reference outputs.

\paragraph{Workload.}
For each task we fix a single input that is identical across LLMs, languages, and
platforms: for EffiBench-X tasks a large input produced by the task's test generator, for
CLBG tasks the parameter $N$. Its size is calibrated in a pilot study such that the C++
reference solution runs for at least \TBD{}\,s on the server, keeping measurements well
above the resolution of the energy counters.

\subsection{Energy Measurement}
On the x86 platforms, energy is read from the Running Average Power Limit (RAPL) interface
through the Linux \texttt{powercap} interface, which exposes cumulative energy counters per
domain~\cite{raffin2024rapl}. We record all domains available on a platform: on the laptop
these are the CPU package (with its core and uncore subdomains) and \emph{psys}, which
covers the whole SoC platform; this laptop CPU has no DRAM domain. \TODO{Server domains
once the server is known.} The Raspberry~Pi~5 offers no RAPL; instead, we sample the
voltage and current channels of its power-management IC at approximately \TBD{}\,Hz and
integrate their summed power over the run. \TODO{If a USB-C power meter is acquired:
describe calibration of PMIC readings against it.}

Because these methods capture different system boundaries, \emph{absolute} energy values
are not compared across platforms. Cross-platform questions (\RQ{3}, \RQ{4}) are answered
using relative measures: LLM rankings, ratios to the reference solution, and energy
normalised within each platform.

\paragraph{Controlled conditions.}
On all platforms, the CPU frequency governor is set to \texttt{performance}, turbo/boost is
disabled where possible, the measured process is pinned to dedicated cores, and
non-essential services are stopped. Before each measurement block, idle power is recorded
for 60\,s; we report both gross and idle-corrected energy. Execution order is randomised
across LLM, language, and task to prevent drift from being confounded with the factors, with
a cool-down of \TBD{}\,s between runs; CPU temperature is logged.
